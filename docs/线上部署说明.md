本平台已部署到亦殃在科技线上服务器，作为门户首屏 **Project 04** 对外展示，
并提供 `/cqm/` 实时演示页。

```

├── reports/                    导出的质量报告（仅保留最新 20 份）

/etc/nginx/sites-enabled/default
```

## 三、进程与端口

| 进程 | 托管方式 | 端口 | 说明 |
|---|---|---|---|
| `yiyangzai-api` | pm2 | 3000 | 原 Node 站点（未改动） |
| Java 后端 | 独立进程 | 8080 | 原 Spring Boot（未改动，`/java-api/`） |
| **`cqm-api`** | **pm2** | **8081** | 本次新增，`MemoryMax` 由 pm2 限制为 180 MB |

> 选用 pm2 而不是 systemd：本机 `/run` 仅 46 MB 且被 systemd 运行日志占用 39 MB，
> 导致 `systemctl daemon-reload` 因空间不足被拒绝。pm2 是站点原有的进程管理器，
> 复用它无需改动任何系统配置。**建议后续为 `/run` 减压**（见"待优化"）。

## 四、内存控制（1 核 512 MB 机器）

启动参数针对小内存做了约束：

```
-Xms16m -Xmx80m -Xss512k
-XX:MaxMetaspaceSize=72m
-XX:+UseSerialGC          # 1 核场景下内存占用最小
-XX:TieredStopAtLevel=1   # 仅 C1 编译，启动快、编译期内存少
-XX:+ExitOnOutOfMemoryError
```

外加 `pm2 --max-memory-restart 180M` 作为兜底：超过阈值自动重启，不会拖垮同机服务。

部署后实测：`cqm-api` 常驻约 **9~73 MB**，原有服务响应正常（已回归验证
`/api/version` 与 `/java-api/health`）。

## 五、数据持续更新机制

`cron` 每 5 分钟执行一次 `run-demo.sh`：以探针方式运行示例应用 18 秒，
向本机 8081 上报运行期指标。因此演示页上的调用次数、耗时与异常率会持续变化。

```
*/5 * * * * /root/cqm/run-demo.sh >> /root/cqm/logs/demo.log 2>&1
```

实测：上报次数 5 分钟内由 6 增至 9，时间戳如期推进。

> 页面展示的是**示例应用（demo-app）**的数据，这是刻意的：
> 用真实业务系统做被监控对象会带来生产风险，示例应用同样能完整验证
> "插桩 → 采集 → 聚合 → 上报 → 规则检测 → 评分 → 展示"全链路。
> 网页上也明确标注了"被监控应用 demo-app"。

## 六、日常运维

```bash
# 查看服务状态
pm2 list

# 查看日志
tail -f /root/cqm/logs/pm2-out.log
tail -f /root/cqm/logs/demo.log

# 重启服务
pm2 restart cqm-api

# 手动触发一次演示流量
/root/cqm/run-demo.sh

# 手动触发静态分析
curl 'http://127.0.0.1:8081/api/analyze?path=/root/cqm/demo/src'
```

更新服务端代码：本地执行 `python build_deploy.py`，上传 `server/classes`，
解包后 `pm2 restart cqm-api`。

## 七、回滚方式

| 改动 | 回滚 |
|---|---|
| nginx | 备份在 `/root/nginx-default.bak.<时间戳>`，覆盖回去后 `systemctl reload nginx` |
| 首页 | 备份在 `/root/index.html.bak.<时间戳>` |

## 八、待优化（已识别，未执行）

1. **`/run` 空间**：46 MB 中 39 MB 被 systemd 运行日志（`/run/log`）占用，
   属于 tmpfs（吃内存）且导致 systemd 无法 reload。建议在
   `/etc/systemd/journald.conf` 中设置 `RuntimeMaxUse=8M` 后重启 journald，
   可释放约 30 MB 内存。**未擅自修改**，需你确认后再动。
2. **swap 使用**：本机已用约 589 MB swap，说明长期内存偏紧；
   若后续访问量上升，建议升级到 1 GB 内存规格。
3. **探针接入真实业务**：如需监控站点自身的 Java 后端，
   可给 Spring Boot 进程挂载探针（改用 `cqm.app=java-backend`），
   但需评估生产风险，建议先在预发环境验证。

## 九、安全机制（上线后加固）

平台对外提供服务后做了一次攻击面测试，**发现并修复了两处真实缺陷**，
现为三层防护：

| 层面 | 措施 | 实现位置 |
|---|---|---|
| 反向代理层 | 写接口 `/cqm/api/metrics`、`/cqm/api/analyze` 一律拒绝外部访问 | nginx `location = ...` |
| 应用层（写鉴权） | 写操作校验 `X-CQM-Token` 请求头，不符返回 401 | 服务端 `-Dcqm.token` |
| 应用层（路径限制） | 静态分析 `path` 参数只能指向 `-Dcqm.src` 目录之内，越界返回 403 | 服务端 `containsSrcRoot` |

**令牌管理**：令牌保存在本机 `deploy_token.txt`，同时写入了服务器的
`run-demo.sh`（权限 700）与服务端启动参数。更换令牌需同时更新两处并重启服务。

**公网实测结果**：

```
构造越界路径 /cqm/api/analyze?path=/etc   -> 403（修复前 200，且能扫描任意目录）
提交伪造数据 POST /cqm/api/metrics        -> 403（修复前 200，且数据被污染）
只读接口 /cqm/api/overview、/api/static   -> 200 正常
```

**修复前的实际影响**（测试后已恢复数据）：攻击者可改写被监控应用名称、
注入虚假方法、覆盖静态分析结果与违规记录（实测违规数被由 3 清为 0），
并使服务端遍历任意目录。

## 十、健壮性修复记录

静态分析器的对抗性测试发现一处**漏报**缺陷：

- **现象**：字符串字面量中出现**不成对**的大括号时（如 `String open = "{";`），
  花括号计数失衡，把其后所有方法并入当前方法。实测一个含 6 个方法的文件
  只识别出 1 个，且该方法有效行数由 3 行膨胀至 24 行。
- **修复**：词法预处理阶段清空字符串/字符/文本字面量的内容（保留引号维持词法边界），
  使字面量中的括号不参与结构判定。
- **回归测试**：`python test_analyzer.py`，14 项断言全部通过。
